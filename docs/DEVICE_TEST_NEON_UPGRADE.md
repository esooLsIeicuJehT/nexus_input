# Neon/controller development candidate — phone checks

The user confirms all affected Stadia buttons already appear in Devices. Test their routing separately on rooted Moto G 2026 (KernelSU) and non-root Moto G 4G 2025 (UID-2000 Shizuku). Use the same installed app signing key and retain existing profiles. The pre-change source archive is in `backups/`; it does not contain the phone's profile data. Export the existing profiles with System → System tools → Local profile files before testing a candidate.

1. Open the existing game profile. In Mapper, select each of Start, Select, Guide/Home, Capture and Assistant, then **Rebind → Learn physical button** and press the actual button. Choose Capture/Assistant first if Android reports an unknown vendor key, so its label remains meaningful. The observed key/scan identity is saved. For D-pad, select the matching `DPAD_*` direction; key events and HAT axes are both supported. Keep the existing stick controls/tuning.
2. Launch the game through the existing mapping action. Verify each target produces the intended game touch; verify D-pad diagonals, release and key/HAT overlap. Check a center button while holding LS, moving RS and holding a trigger. Check the existing macro, turbo and panic actions. Capture in Devices alone is not successful game injection.
3. Open the floating mapper; verify Add, Bind, Learn, Delete, Size, Save, Cancel and Panic remain reachable. Save one learned binding, reload the profile and confirm its key/scan identity persists. Rotate the phone and confirm the bubble stays reachable and the main mapper keeps its single bottom dock.
4. System → Diagnostics → Collect, then Copy report. The report includes the selected profile's bindings, raw controller events and actual runtime backend. If a target still fails, collect after pressing that button and include whether failure occurs on root, Shizuku or both. `adb logcat -s NexusRouting NexusInput` shows binding misses and matched touch requests; these request logs are not proof a game accepted a touch.
5. KernelSU WebUI → Updates → Check should advertise `1.1.0-dev`/1100 once this candidate is published. Update stages the verified module and requests a reboot. After reboot, check the installed version, each WebUI page and existing controls. Inspect root frequency values before/after any deliberate change; thermal controls and active ZRAM resizing remain unavailable. No preset should be applied merely by opening a page.

Review whether the main pages fit, diagnostics stay within their own window, and small-screen/landscape controls remain reachable. Minor page scrolling is allowed; large reports should scroll inside their window. This candidate uses static edge lighting in the APK/gameplay overlay to preserve the tested input loop, with WebUI backdrop blur. No physical-device performance measurement is claimed by the host/CI tests.
